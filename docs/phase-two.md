# Blink 二期实施计划

基线日期为 2026 年 11 月 23 日。二期交付账号、四端数据互通、应用更新和服务端运维。用户安装后仍可直接离线使用；在第二台设备上登录同一账号，才需要接触同步。首页继续只展示当前模式和一个倒计时。

## 从哪里开始

| 已有能力 | 二期需要补齐 |
| --- | --- |
| Android、iOS、Windows 11、macOS 有离线客户端及构建流水线。工作计时、午休与晚餐、非工作模式、记录和提醒在本地运行。 | 四端账号入口、持久化同步队列、本地数据迁移、正式签名和应用内更新入口。 |
| 成都 ECS 上已有仅监听回环地址的测试 API、SQLite 数据库、systemd 服务及带健康检查的升级脚本。 | 客户端通过受控隧道联调，服务端持续集成、自动部署、备份恢复和生产 HTTPS。 |
| 账号 API 已支持注册、登录、退出。打卡 API 已用两个独立会话验证分页、重传、撤销与账号隔离。 | 真实客户端互通；作息、临时安排、用眼区间和手动修正的数据协议；找回账号、撤销设备和删除账号。 |

测试服务的既有验收是接口级验证。第一项新交付是让用户亲手在 Android 上记一次喝水，然后在 Mac 的「记录」中看到它。[现有服务协议](../server/README.md) · [一期交互规格](phase-one.md)

## 里程碑、依赖与验收

以下为一名开发者连续工作的初估，从开始实施起算。各阶段共约 **24–36 个工作日**，证书、域名、商店审核和测试设备的外部等待另计。每阶段结束以可运行版本和验收记录交付，再按实测更新余量。

| 阶段 | 工作与交付物 | 通过条件 | 估算 |
| --- | --- | --- | --- |
| M1 内网联调与迁移准备 | 在 Mac 和 Android 测试包分别配置受控隧道；分离测试和正式地址；本地存储加版本号、迁移前快照、按账号分区的待上传队列。确定稳定 Android 测试签名及旧签名包的数据转移路径。 | 两端均能访问内网健康接口；升级旧数据样本后，记录数、作息和每日总量一致；无网冷启动仍能计时。 | 2–3 天 |
| M2 账号与打卡闭环 | 「日程」增加折叠的「账号与同步」。接入注册、登录、退出、会话到期和重新登录。系统凭证存储保存令牌；首次登录只询问一次是否合并本机记录。前台打开、网络恢复、打卡后自动同步。 | Android 离线打卡再联网，Mac 出现一条；Mac 撤销后，Android 重启也不会恢复旧记录。切换账号无串账，退出单台设备不影响另一台。 | 4–6 天 |
| M3 完整业务数据互通 | 完成下表的数据模型；服务端提供版本迁移和增量读取；客户端合并后再刷新统计、重排本地通知。加入时钟偏差、并发修改、跨零点和历史数据回放测试。 | 两台设备的同一天总量、打卡、作息和临时安排一致；午休和晚餐不计入工作用眼；同步失败时本机提醒仍按时工作。 | 6–9 天 |
| M4 服务端发布与恢复 | 服务端测试纳入 CI；指定提交自动发布测试环境，正式版由受保护的发布操作触发；使用限实例、限命令的部署身份。分离测试与正式数据库、凭证和备份。增加访问限流、会话撤销、密码修改、一次性恢复码、数据导出与注销。 | 模拟一次错误发布和一次空库恢复；可回退服务、读回备份；确认注销会撤销会话，离线旧设备无法回传已删除账号的数据。 | 4–6 天 |
| M5 四端更新 | 建立测试／稳定两个渠道和版本清单，接入下表的各平台更新路径；设置页查看版本、发布说明、更新或稍后。 | 每个平台用上一版实际升级一次，账号、离线队列和记录保留；下载中断可重试，签名错误的包无法安装。 | 4–6 天 |
| M6 四端验收与分批上线 | Android 与 Mac 先内测，再接 Windows 11 与 iPhone。跑完离线、同步、提醒、升级与恢复矩阵。域名就绪后验证正式入口，先开放小范围测试，再推广稳定版。 | 四端验收表有设备、系统版本和结果；无数据丢失、跨账号泄露、重复累计或破坏性升级；发布记录包含回退版本。 | 4–6 天 |

**实施顺序。** M1 → M2 是首个可体验版本，预计 6–9 个工作日。M3 依赖 M2 的账号隔离和本地队列。M4 的备份、CI 和 M5 的签名准备可从 M1 开始穿插；M6 依赖业务同步、运维和更新全部通过。没有域名时，M1–M5 可在内网或测试渠道推进。

## 数据如何同步

| 数据 | 建议实现与用户可见结果 |
| --- | --- |
| 远眺、离席、喝水打卡 | 沿用现有 UUID。一条打卡重试上传仍为一条；撤销也同步并优先于旧设备的重传。独立手动打卡分别保留，避免误删真实记录。 |
| 今日用眼估算 | 从二期起按设备记录有效起止区间，按北京时间分日。账号总量取区间并集。例如手机 09:00–09:30、电脑 09:10–09:40，共 40 分钟。每台设备先扣除自己的午休、晚餐、远眺和离席暂停。 |
| 一期历史总量与修正 | 旧数据只有每日总量，无法还原精确重叠。建议首次合并时选一台设备作为迁移日前历史基准，预览导入天数及差异；其他设备仍可导入有标识的打卡。迁移当天用明确切换时刻衔接基准和新区间。手动修正保存为当日目标总量及其修正时的基准，之后新增时长继续累计。 |
| 固定作息和提醒频率 | 上下班、午休、晚餐作为一组原子更新，防止产生交叉时段；提醒频率按项同步。并发编辑同组时保留服务器已确认版本，向后提交的一端展示两版，允许保留自己的修改。法定工作日和调休日沿用同版日历。 |
| 当天临时安排与手动上下班 | 临时安排有独立 ID，编辑、完成、删除均可同步。当天取消自动上班等账号级例外包含生效和过期时间；晚到的昨天操作不能改变今天模式。 |
| 当前计时与通知 | 建议非工作定时用眼由发起设备执行，完成的有效区间汇入账号。普通用屏继续按各平台可观察范围估算。声音、震动、锁屏可见性、系统权限、主题按设备保存；同步历史打卡不会触发补发通知。在线时同步同一轮提醒的确认状态；两端均断网时可能各自提醒，联网后合并同轮确认。 |

客户端把业务变更和待上传操作一起持久化，账号、设备、游标和队列关联保存。先落盘一页数据，再移动同步游标；断网、超时或进程中断后从已确认位置重试。现有接口每页最多 200 条。新增数据类型带协议版本，旧客户端可继续使用已有打卡接口。跨账号登录时分别显示本机待合并数据和当前账号数据，只有用户选择后才合并。

## 四端更新交付

| 平台 | 计划路径 | 特有验收 |
| --- | --- | --- |
| Android | 建立长期签名，测试和稳定渠道发布有版本号的 APK，用户确认系统安装。 | 同签名覆盖安装保留数据；旧 CI 随机签名包先实际验证导出、导入，再执行替换。[Android 签名说明](https://developer.android.com/studio/publish/app-signing) |
| iOS | 内测用 TestFlight，正式版走 App Store。应用展示版本说明并跳转对应渠道。 | 主应用和锁屏扩展均能签名，iPhone 上完成上一版升级、首次登录和锁屏提醒验证。[Apple TestFlight](https://developer.apple.com/testflight/) |
| Windows 11 | 稳定渠道提供已签名的 x64 安装程序，检查版本后由用户确认升级。 | 运行中可推迟更新；升级后托盘、右下角打卡、离线队列可用。 |
| macOS | 稳定渠道提供签名并公证的通用包，先交付可验证的下载安装流程。 | 实机验证替换旧版、系统凭证和记录保留；覆盖 Apple Silicon，并安排 Intel 兼容验证。 |

发布清单包含平台、架构、渠道、版本、最低兼容版本、下载地址、摘要和说明。正式安装包存放在有版本的发布地址，签名或签名清单用于验证来源。更新检查可稍后处理，失败时继续使用已安装版本。

## 部署、运行和公开条件

- **无域名阶段**沿用成都 ECS、SQLite 和 systemd。开发电脑通过受控隧道访问回环服务，Android 调试机通过本机端口转发联调。正式包单独配置可信 HTTPS 地址，测试地址不随正式包发布。
- **有域名阶段**配置 DNS、HTTPS 反向代理、证书续期以及告警；确认所选地域和发布渠道适用的备案、隐私及上架条件后再开放注册。数据库和内部服务端口保持私有。
- **自动部署**先运行服务端集成测试，校验固定版本制品，再迁移、重启、检查健康接口和认证接口。数据库变更采用向后兼容迁移，破坏性变更另行安排恢复演练。代码回退和数据库恢复分别验证。
- **备份与运行指标**建议内测目标为每日加密异机备份，最多容忍 24 小时服务端数据回退，4 小时内恢复。发布前在空环境演练一次，核对账号、打卡、撤销和游标；恢复旧快照时让客户端识别数据库代次并重新对账。关注同步失败、备份时效、磁盘余量、证书到期；日志排除密码、令牌和个人记录正文。[SQLite 一致性备份](https://www.sqlite.org/backup.html)

## 验收和责任

| 验收场景 | 要观察的结果 |
| --- | --- |
| 首装、游客升级、换机、A/B 账号轮换 | 本地先用；首次合并可预览；重登恢复自己的数据，待传数据保持正确归属。 |
| 两端离线 24 小时、超过 200 条、上传成功但响应丢失、拉取中途重启 | 队列最终清空，逐项核对记录无丢失或重复，撤销无复活。 |
| 双端同时用眼、跨日、午休晚餐、调休上班、提前下班、手动修正 | 两端最终显示相同数字，重叠示例为 40 分钟，修正后新增用眼仍可累计。 |
| 服务不可用、令牌过期、退出登录 | 本地计时与提醒持续工作；联网或重新登录后恢复同步；首页无反复弹窗。 |
| 真实设备与发布 | Android 和 Mac 验证双向同步，再用 iPhone 和 Windows 11 复测；各端做一次跨版本升级。模拟器、CI 结果和真机结果分别记录。 |

开发和部署由项目开发侧承担。项目所有者在相应阶段提供固定签名材料的安全存放位置、Apple 开发者与分发授权、真机测试条件，以及公开发布时选用的域名和 DNS 权限。付费服务和证书采购单独确认。优先落实 Android 固定签名和旧数据迁移；没有域名不影响首轮双端验收。

## 2026-11-23 安卓内测验收

| 检查项 | 实测结果 |
| --- | --- |
| 内网入口 | 手机经 USB → Mac → 限定 SSH 隧道访问成都 ECS；Mac 通过健康检查。安全组仅增加开发 Mac 单地址至 SSH 的入站规则。 |
| 注册、离线、恢复连接 | 小米 2106118C，Android 14。独立测试账号断开转发后打卡，恢复后服务端出现一次；第二个接口会话撤销后，手机同步移除。第二会话运行于 Mac 测试工具。 |
| 覆盖升级 | 0.2.2 升至 0.2.3 前先离线打卡、重载并验证落盘；升级后读回同一账号和待传打卡，联网只上传一次。真机读取更新清单返回本机版本 3、渠道版本 3。覆盖安装由 ADB 发起。首次 0.2.1 → 0.2.2 测试立即覆盖后未读回临时样例，旧签名迁移须先导出并核对备份。 |
| 一期数据 | 原包在机保留。测试机原游客样本有 1 天估算、0 条打卡，已在 Mac 上单独导出，在内测游客空间核对了作息和估算；未上传至云账号。 |
| 发布与恢复 | 服务端发布经过测试、CI 签名、ECS 主动验签切换。隔离 SQLite 样本完成加密备份和恢复，核对账号、记录、撤销、会话清空及新代次。 |
| 后续验收 | 每日异机备份的首次实际交付、两台真机的同步提醒、实际 24 小时断网及从应用内触发系统安装器完成升级。iOS、Windows、macOS 客户端联调和正式域名上线留待对应阶段。 |

0.2.4 已在同机覆盖 0.2.3，升级前后分别读到渠道版本 4、本机版本 3 和 4，游客数据再次核对通过。两个独立会话在 ECS 对同一轮工作提醒提交不同确认时间，最终仅保留首次确认。Linux CI 的错误发布演练强制健康检查失败，并验证切回前一版本、重新启动。
